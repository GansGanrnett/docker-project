# Правила работы с репозиторием

## Коммиты

Тема коммита — не длиннее 72 символов. Тело начинается после пустой
строки и этим лимитом не ограничено.

## MongoDB Driver

Для миграций использовать только простейшие типизированные операции:
`Find(...).ToListAsync()` по полным моделям и `UpdateOneModel<T>` /
`BulkWriteAsync`.

Не использовать:

- raw-BSON в запросах и обновлениях,
- проекции на computed fields,
- `$`-ссылки в классическом `$set` (сервер разворачивает поле-ссылки
  только в aggregation pipeline, а не в обычном `$set`),
- `BsonDocument` в проекциях.

Если нужна продвинутая функция — сначала проверить API локальным probe,
потом коммитить.

## Моки не заменяют реальный API

Если задача касается внешнего API (брокер, БД, HTTP-клиент, SDK) и нет
полной уверенности, что метод существует и ведёт себя так, как ожидается:

1. **Проверять API фактически** — документация, `dir()`, локальный probe
   или простой скрипт. Не полагаться на память и интуицию.
2. **Не писать мок на метод, существование которого не подтверждено.** Мок
   выдуманного API создаёт ложную уверенность: тесты зелёные, код сломан.
3. **Integration-тесты с реальной зависимостью обязательны** для критичных
   путей — публикация, транзакции, dead-letter. Unit-тесты с моками
   дополняют, но не заменяют.
4. **Если локально поднять зависимость нельзя** (нет Docker) — переносить
   проверку в CI как обязательный шаг. Живой брокер или БД в CI дешевле,
   чем баг в проде.

Основание: сессия #37, коммит 2 (PR #44). `BlockingChannel.wait_for_confirms()`
в pika 1.3.2 не существует — в confirm-режиме `basic_publish` сам блокируется
до ответа брокера и поднимает `NackError` / `AMQPError`. Unit-тесты с моками
прошли зелёными, потому что заглушка определяла тот же выдуманный метод: мок
и был спецификацией. Integration-тест на живом RabbitMQ упал сразу, поймано
в CI.

Основание: PR #42 (issue #34). Миграция статусов заказа потребовала пяти
раундов правок именно из-за этих четырёх приёмов — `$ifNull` сохранился
как литерал, `BsonDocumentArray` в драйвере 2.23 отсутствует, `$CreatedAt`
записался строкой, проекция на класс без BSON-атрибутов молча вернула
дефолты, `BsonDocument` в проекции не перевёлся вовсе. Рабочий вариант —
чтение полных типизированных моделей плюс `BulkWrite`. Лишние поля в
памяти на разовом скрипте дешевле кода, поведение которого нельзя
предсказать.

## Автономный merge

Агент вправе сам смержить PR, которые он сам создал в текущей сессии.

**Разрешено:**

- merge PR собственного авторства в `main`,
- только при зелёном CI: все чеки `success`,
- только merge-коммитом (не squash, не rebase) — история сохраняется,
- удаление feature-ветки после merge, локально и на remote,
- закрытие связанных issue.

**Запрещено:**

- merge чужих PR, даже при зелёном CI,
- merge при красном CI, `pending` дольше 10 минут или `mergeable: false`,
- merge в `project` или напрямую в feature-ветку — только PR в `main`,
- force-push,
- merge при конфликтах с `main` — сначала разрешить конфликт.

Если CI зелёный, но diff вызывает вопросы (неожиданные файлы, странные
метрики, сомнительные правки) — стоп, показать и спросить.

## Проверка после правок

После каждого блока правок — приложить `git status --short` и
`git diff --stat` перед тем, как сообщить «готово». Нет вывода — правка не
считается сделанной. Если `git status` пуст, а правки должны были быть,
разобраться и не сообщать об успехе.

Основание: PR #43 (issue #34). Расхождение между отчётом и реальным
состоянием файлов стоило лишнего раунда работы: правка была объявлена
готовой без единой команды, которая бы это показала. Стоимость проверки —
две команды, стоимость ошибки — потерянный раунд.
