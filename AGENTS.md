## Принципы работы

### Доказательство, а не утверждение

После каждого блока правок — приложи `git status --short` и
`git diff --stat` перед тем, как сообщить «готово». Нет вывода — правка
не считается сделанной. Если `git status` пуст, а правки должны были
быть — разберись, не сообщай об успехе.

Стоимость проверки — две команды. Стоимость ошибки — потерянные раунды.

### Сначала пойми, потом делай

Если задача касается внешнего API, протокола, формата данных или
инфраструктурного компонента, в котором ты не уверен:

1. Разберись, как это работает **на самом деле** — по документации,
   по коду, локальным probe, а не по интуиции.
2. Если поведение неочевидно — нарисуй схему (поток данных, порядок
   вызовов) и покажи перед реализацией.
3. Проверь крайние случаи: пустые значения, отказы, конкуренцию.
4. Только после этого пиши код.

Не полагайся на «кажется, работает». Продвинутые приёмы API оправданы
только когда простой путь действительно не подходит, и ты можешь
объяснить почему.

### Моки не заменяют реальный API

1. **Проверять API фактически** — документация, `dir()`, локальный probe.
   Не полагаться на память и интуицию.
2. **Не писать мок на метод, существование которого не подтверждено.**
   Мок выдуманного API создаёт ложную уверенность: тесты зелёные,
   код сломан.
3. **Integration-тесты с реальной зависимостью обязательны** для
   критичных путей — публикация, транзакции, dead-letter. Unit-тесты
   с моками дополняют, но не заменяют.
4. **Если локально поднять зависимость нельзя** (нет Docker) —
   переносить проверку в CI как обязательный шаг.

Основание: сессия #37, PR #44. `BlockingChannel.wait_for_confirms()`
в pika 1.3.2 не существует. Двадцать unit-тестов прошли зелёными,
потому что заглушка определяла тот же выдуманный метод. Integration-тест
на живом RabbitMQ упал с первого прогона.

### Минимум сложности

Простые решения дешевле в поддержке. Оптимизация без измеримой
необходимости — преждевременна. При выборе предпочитай вариант, где:
меньше движущихся частей, меньше зависимостей от неочевидного поведения,
легче откатить, проще объяснить.

### Один PR — одна задача

Слабо связанные правки — отдельно. Если нашёл что-то ещё по ходу —
фиксируй отдельным issue, не тащи в текущий PR.

## Git

- `main` — стабильная. Работа идёт в feature-ветках или `project`.
- Прямой push в `main` и `project` запрещён. Только через PR.
- Коммиты и push — по правилам режима (см. [AUTO] или обычный).
- Force-push, push в main/project — только по явному подтверждению.

### Контекст gh

`gh` определяет репозиторий по git-remote текущего каталога. Рабочий
каталог сессии — внутри Obsidian-vault, то есть репозиторий другой.
Всегда указывай репозиторий явно: `gh <команда> -R GansGanrnett/docker-project`.

### Автономный merge

Можно мержить самостоятельно только собственные PR в `main`:

- при зелёном CI (все чеки `success`),
- обычным merge-коммитом (не squash, не rebase),
- с удалением feature-ветки после merge,
- с закрытием связанных issue.

Нельзя: мержить чужие PR, мержить при красном CI или затянувшемся
`pending`, мержить при конфликтах, force-push. Если diff вызывает
вопросы — стоп и спроси.

При stacked PR: базовая ветка вливается merge-коммитом, не squash.
Не удаляй базовую ветку, пока на ней стоят зависимые PR.

## Безопасность

Никогда не выводи содержимое файлов, похожих на секреты: `.env`, `*.pem`,
`*.key`, `id_rsa`, `credentials.*`. Если такие файлы попадают в задачу —
упоминай только путь и тип.

## Обработка ошибок

1. Перед выполнением команды — не пиши анонсов. Сразу выполняй.
2. При ошибке: полный текст (stderr), сама команда, код возврата,
   одна альтернатива если очевидна.
3. Если команда не может быть выполнена: «Не могу выполнить: причина»,
   текст ошибки, ручной вариант, стоп и ожидание.
4. Не повторяй одну и ту же упавшую команду больше двух раз.
5. Не пиши «сейчас попробую», «запускаю». Выполняй и показывай результат.

3. При неоднозначной задаче — уточняющий вопрос (кроме [AUTO]).

## Таймаут shell-инструмента (~2 минуты)

Не запускать длинные многошаговые циклы с сетевыми вызовами (gh, curl,
git fetch) в одном shell-вызове — таймаут. Дробить: один вызов — одна
команда или один маленький цикл (< 30 секунд). При работе с gh
использовать `--limit 10` и `--json`, не `--paginate`.

## Если директива противоречит фактам

Проверь директиву по коду перед выполнением. Если противоречит:

- Файл уже в main → «уже сделано в PR #N»
- Ветка уже удалена → «ветки нет, проверил `git branch -a`»
- Метрика не экспортируется → «её нет, нужен другой SLI»
- Issue закрыт → «закрыт в #N»

Не выполняй слепо. Не выдумывай обходной путь. Останавливайся и
показывай противоречие.

## План принят — иди до конца

Если я ответил «план принят», «ОК», «[AUTO]», «дальше» — выполняй до
полного завершения. Не показывай план повторно. Не спрашивай
подтверждения на каждом шаге. Отчёт — один в конце.

## Первое действие в новом чате

Перед любой задачей — проверь фактическое состояние:

```
gh issue list --state open --limit 20
gh pr list --state open --limit 10
```

Не полагайся на `docs/audit-*.md` — это снимок, не текущее.

## Автономный режим (когда задача помечена [AUTO])

Если в начале задачи стоит маркер `[AUTO]`:

1. Работай до полного выполнения задачи. Не останавливайся для
   подтверждений на каждом шаге.
2. Сам выбирай лучший вариант из альтернатив. Обоснование — 1 строка.
3. Останавливайся ТОЛЬКО при:
   - необратимое действие (force-push, удаление данных, merge в
     защищённую ветку) — кроме автономного merge своего PR;
   - 2+ провала CI подряд с одной и той же ошибкой;
   - противоречие в требованиях;
   - нашёл проблему, которая меняет план (нужен новый дизайн);
   - директива противоречит фактам (см. выше).
4. В остальных случаях: делай → коммит → push → PR → CI → merge.
5. Отчёт — ОДИН в конце. Не пиши «сейчас попробую», «жду подтверждения».
6. Не пересказывай план несколько раз. Если план принят — выполняй.
7. Максимум итераций: 10. Если после 10 не сделано — стоп, отчёт.
